## Decisions not in the spec

- **dj-stripe 2.11.0 works here** (Django 6.0.8, Python 3.14.8). `uv add "dj-stripe>=2.11,<2.12" stripe` installed dj-stripe 2.11.0 and stripe 15.6.1 (dj-stripe requires `stripe>=15.0.1,<16`). Its classifiers name Django 5.2 and 6.0; the product spec says 6.0 and 6.1.
- **dj-stripe 2.11 keeps most Stripe fields in a `stripe_data` JSON column.** `Subscription.status` and `trial_end`, `SubscriptionItem.quantity` and `Price.type` are properties, not columns. So `get_stripe_subscription()` filters on `stripe_data__status` (Read the Docs' `filter(status=...)` no longer works), and the plan list filters on `stripe_data__type="recurring"`.
- **Subscription priority** is the spec's: active, past_due, trialing, incomplete, then the latest of any status (Read the Docs puts unpaid and past_due first). Within one status the most recently created wins. If a status has more than one subscription, it logs an ERROR with the team id, because both are being billed.
- **dj-stripe settings:** only `DJSTRIPE_FOREIGN_KEY_TO_FIELD = "id"`, which its system check (`djstripe.E002`) requires for a new installation. Everything else stays at dj-stripe's defaults: webhooks are validated by signature, `STRIPE_API_VERSION` is stripe-python's pinned version (`2026-05-27.dahlia`), and dj-stripe's subscriber model stays the user model, unused, because customers are linked to teams through `Team.stripe_customer`.
- **Our foreign keys to dj-stripe point at its primary key** (`djstripe_id`), as Read the Docs' do: `Team.stripe_customer`, `Team.stripe_subscription` and `ProductFeature.product`. dj-stripe's own foreign keys point at the Stripe id. That is why `get_feature` matches items with `price__product__pk__in`.
- **The webhook URL is `stripe/webhook/<uuid>/` among the shared routes** (`project/urls.py`), so it answers on every site's domain. Register it on the productivity domain. A request to plain `localhost` would be redirected by the multisite middleware, and Stripe does not follow redirects.
- **Dev helper: dj-stripe's own `manage.py stripe_listen`, not a new command.** dj-stripe 2.11 ships `stripe_listen --host --port`. It runs `stripe listen --print-secret`, stores the CLI's signing secret in a temporary `WebhookEndpoint`, forwards events to that endpoint's URL and deletes the endpoint on exit. A command that only printed a `stripe listen --forward-to ...` line would not work: `stripe listen` signs events with its own secret, and dj-stripe rejects every event (400) unless that secret is in a `WebhookEndpoint` row. `.env.example` gives the line for this checkout: `uv run manage.py stripe_listen --host productivity.localhost --port $DJANGO_PORT`. Here it stops with "The Stripe CLI binary 'stripe' is not installed."
- **`get_or_create_stripe_customer(team, email)` takes the email** of the admin who starts Checkout. The spec says "the admin's email", but a team can have several admins. It locks the team row while it creates the customer, so two admins who start Checkout at the same moment get one customer. Without the lock, the second save would unlink the customer the first admin pays with, and that payment would never reach the team. The lock is held for one Stripe call. A customer deleted in Stripe stays in dj-stripe's table, marked `date_purged`; the team then gets a new customer instead of failing on the dead one forever. (Added after code review.)
- **Checkout asks Stripe for the customer's subscriptions first** (`stripe.Subscription.list(customer=..., status="all")`) and refuses when any is in a status other than `canceled` or `incomplete_expired`: "already has a plan. Change it in Manage billing." Stripe has the subscription as soon as a Checkout is paid, while its webhook may still be on the way, so the stored `team.stripe_subscription` alone could not stop a second purchase. That is one more Stripe call per Checkout. The Billing page shows no plans while the team's plan is live, and none on the `?checkout=success` return while it shows "processing". Plan changes go through the portal. The posted price must be one of this site's active recurring prices in the current mode (`livemode=STRIPE_LIVE_MODE`), otherwise 404. (The Stripe check and the hidden plans were added after code review.)
- **The Checkout session also gets `metadata`**, the same dict as `subscription_data.metadata`, so `checkout.session.completed` carries `team_id` for the handler's fallback too. The metadata values are strings (`"team_id": "5"`): Stripe metadata holds only strings, and stripe-python's types say so.
- **Trial: once per team.** `trial_period_days` comes from the price's metadata, else the product's. A price's `"0"` turns off its product's trial, and with neither there is no trial. A customer that already had any subscription, even a canceled one, gets no trial, so cancelling at the end of a trial and subscribing again does not start another free trial. **This changes what a user can do, so it is your call** (see Code review). Checkout always collects a card (its default), so there are no card-less trials.
- **Return URLs:** success is `<billing page>?checkout=success`, cancel is the Billing page, both from `request.build_absolute_uri`. With `?checkout=success` the page shows "Stripe is processing your payment" until the team has an active, trialing or past_due subscription.
- **Portal:** 404 when the team has no Stripe customer (the button only shows when it has one). `configuration` is `SITES[site_key].get("stripe_portal_configuration")`. No site has that key yet, so it is None, stripe-python leaves the parameter out, and Stripe's default portal applies. `SITES` gets no new key here; 07-site-billing adds it.
- **No try/except around Stripe calls.** A Stripe error answers 500 and reaches Sentry with its traceback. Read the Docs catches every exception and shows a flash message instead; the fail-loud rule wins here.
- **Webhook handler:** one receiver for the four events. An event without a customer (a Checkout from a payment link, say) is ignored, since a team always has one. It finds the team whose `stripe_customer` is the event's customer. The fallback by the metadata's `team_id` only takes a team that has no customer yet, and links it. With no team it logs an ERROR with the event id, type and customer id, and the event still succeeds; raising would make Stripe retry it for days. The team row is locked (`select_for_update`, inside dj-stripe's per-event transaction), so two webhooks for one team cannot save a stale pick. Example: `checkout.session.completed` reads before `customer.subscription.created` commits and saves after it.
- **Order of receivers:** dj-stripe connects its own receivers in its `ready()`, and `djstripe` comes before `apps.billing` in `INSTALLED_APPS`, so dj-stripe has synced the subscription before our receiver re-picks.
- **Only the items Stripe currently reports count.** dj-stripe 2.11 never deletes a subscription item that was removed upstream (its `_stripe_object_to_subscription_items` says so, because old invoices still point at it). `current_items()` keeps the items whose ids are in the subscription's stored `items.data`, and `get_feature` and the Billing page's plan both use it. Without it, a team moved from Pro to Basic in the Stripe dashboard would keep Pro's features. (Added after code review.)
- **`get_feature`** raises `ValueError` for another site's key (not `assert`, which `python -O` removes) and `Feature.DoesNotExist` naming the key for an unknown key. A paid plan's value replaces the free value; it is not added to it. If the subscription has no item whose product has the feature, the free value applies. If matching products give 0, the result is 0, not the free value: the product turns the feature off on purpose.
- **`feature_required` sends members to the team's home page, not to Billing.** Admins go to Billing with "Your plan doesn't include this. Choose a plan to use it." Members go to `/a/<slug>/` with "Your team's plan doesn't include this. Ask an admin to upgrade." The spec says Billing for everyone, but Billing is admin-only, so members would have landed on a 403.
- **Validation** is in `Feature.clean()`, which the admin runs: the site must be in `SITES` (Django's `example.com` row is in the dropdown but not in `SITES`), the key must start with its site's key and a dot, and an on/off feature's free value is 0 or 1. `free_value` and `value` are `PositiveIntegerField`s. A `ProductFeature` is not checked against the product's `metadata.site`.
- **Admin:** `Feature` with a `ProductFeature` inline (product, value). `ProductFeature` has no admin page of its own, and dj-stripe's Product admin is unchanged. On the Team admin page, `stripe_customer` and `stripe_subscription` are read-only: saving a form opened before a webhook would otherwise write the old subscription back. (Added after code review.)
- **No data migration for the demo feature.** Site rows come from `sync_sites`, which runs after `migrate`, so on a fresh database a migration cannot find the productivity Site. The owner adds `productivity.export` in the admin (see What the owner needs). Until then the export page raises `Feature.DoesNotExist` and answers 500, following the spec's "unknown keys raise".
- **Pages:** a Billing tab in the team tabs, shown to admins only. The demo gate `/a/<slug>/export/` is in the productivity site's URLs only, so it is 404 on the directory.
- **Production settings require `STRIPE_LIVE_MODE` and the secret key of that mode:** `STRIPE_TEST_SECRET_KEY`, or `STRIPE_LIVE_SECRET_KEY` when live mode is on. An unset `STRIPE_LIVE_MODE` raises, so production cannot drift into test mode, where anyone can pay with Stripe's public test card (the mode was required after code review). django-environ reads a set-but-empty value as False, so a Render prompt left blank still means test mode. The public keys stay optional, because nothing reads them (Checkout and the portal are server-side redirects). CI's production check gets `STRIPE_LIVE_MODE=False` and a dummy test key. `render.yaml` gets all five keys as `sync: false` prompts on both services.
- **mypy:** `djstripe.*` is in the `ignore_missing_imports` list (dj-stripe has no `py.typed`). The portal's optional configuration is `cast(str, ...)` because stripe-python's types want a `str`, and stripe-python drops a None parameter when it encodes the request.
- **Tests (32 in `apps/billing/tests`).** The webhook tests send events through dj-stripe's `Event.process`, which is what its webhook view calls once the signature is valid. `stripe.Subscription.retrieve` is mocked to return Stripe's current state, and an `APIKey` row with its `Account` is in the database so dj-stripe does not fetch the account. dj-stripe re-retrieves each object when it handles an event, so the late-older-event test checks both the re-pick and that the stored status is Stripe's current one. dj-stripe's own tests mock `stripe.<X>.retrieve` the same way (`tests/stripe_world.py`). The other tests build dj-stripe rows directly in the database.
- **Source comments** name Read the Docs (Team fields and `get_stripe_subscription`, `utils.py`, the handlers, the views, `get_feature`) and School Desk (mocking Stripe in the module that calls it, in `test_views.py`), all MIT.

## Things you should know

- **Two Checkout sessions opened before either is paid both still go through, and both are billed** (two tabs, or two admins). Once one is paid, Checkout refuses new ones, because it asks Stripe. But a Checkout page that is already open can still be paid. `get_stripe_subscription` then picks one and logs an ERROR, and the other has to be cancelled in Stripe. Preventing it would need expiring the team's open Checkout sessions when one completes.
- **Switching `STRIPE_LIVE_MODE` on a database that has test-mode data:** teams keep their test customer and test subscription. Checkout would then fail on the test customer, and a test subscription that was active keeps its features, because no test webhooks arrive any more. Before going live on a database that was used in test mode, unlink them: `Team.objects.update(stripe_customer=None, stripe_subscription=None)`.
- **Every checkout that forwards webhooks with `stripe listen` gets every event of the Stripe account**, other worktrees' included. dj-stripe stores those customers too. Our handler logs "no team for customer" for them, except when the spec's `team_id` fallback finds a local team with the same id and no customer, which it then links. Locally that means two worktrees that share one test account can cross-link teams. See Code review.
- **Choosing a plan in development without keys calls Stripe with an empty key.** Stripe answers 401 and the page 500s. I did not click it here, because it would reach api.stripe.com.
- **Stripe is called during syncs:** once per API key to fetch the account, and once per webhook event to re-retrieve its object. The handlers are synchronous, as in Read the Docs.
- **`get_feature` runs three to four queries per call** (feature, subscription, values, items); the demo gate calls it once per request. The `shortcut:` comment in `features.py` says when to add a cache.
- **Pegasus files touched:** `project/settings.py` (`djstripe` and `apps.billing` in `INSTALLED_APPS`, the Stripe block), `project/urls.py` (two includes), `templates/teams/components/team_tabs.html` (ours, the Billing tab), `pyproject.toml` (dependencies, the mypy list).
- **Dev database:** the djstripe (0001 to 0003), `billing.0001` and `teams.0002` migrations are applied. The end-to-end rows (three `billing-e2e-*` users, their team, three products and prices, a customer, a subscription, the feature, a webhook endpoint and its trigger, admin log entries, sessions) were deleted afterwards. I also deleted 18 session rows of users that no longer existed: those of my first run's users, whose cleanup missed their sessions, and those left by earlier sessions' end-to-end users. The dev database again has the same 3 users and no teams, products or features.

## Code review

`/code-review medium`, with the django-ship repository and the range `ec4e944..HEAD` plus the working tree named in the arguments. All 15 findings were about django-ship files.

Fixed:

- `get_feature` counted subscription items Stripe had removed, because dj-stripe 2.11 keeps them, so a downgraded team kept the old plan's features. It now counts only the items in the subscription's stored `items.data`. Test: `test_items_removed_in_stripe_no_longer_count`.
- The Billing page showed the oldest item's product as the plan, for the same reason. It uses the current items too.
- A second subscription could be bought while the first one's webhook was on the way: the return page still listed the plans, and Checkout only checked the stored subscription. Checkout now asks Stripe, and the page hides the plans while it shows "processing". Tests: `test_checkout_refuses_another_sites_price_and_a_second_plan`, `test_return_from_checkout_shows_processing_until_the_webhook`.
- A team could cancel at the end of a trial and start the trial again, as often as it liked. A customer with an earlier subscription now gets no trial. **Your call:** this is a product rule the spec doesn't state. Removing `and not earlier` in `apps/billing/views.py` brings back a trial on every new subscription. Test: `test_trial_once_per_team_and_a_price_can_turn_it_off`.
- A price's `trial_period_days = "0"` was sent to Stripe as 0, which Stripe rejects. Now 0 means no trial, and a price's 0 overrides its product's trial. Same test.
- Production fell back to test mode when `STRIPE_LIVE_MODE` was unset. It is now required there, and CI sets it.
- A customer deleted in Stripe stayed linked (dj-stripe only marks it purged), so Checkout failed on it forever. The team now gets a new customer. Test: `test_a_customer_deleted_in_stripe_is_replaced`.
- The Team admin showed `stripe_customer` and `stripe_subscription` as editable dropdowns, and a save could write a stale subscription back. They are read-only now.
- `Feature.clean` raised `KeyError` (admin 500) for a Site row that is not in `SITES`. It is now a validation error on the site field. Covered in `test_key_must_start_with_the_site_key`.
- Events without a customer (a payment link's Checkout) logged "no team for customer None" at ERROR. They are now ignored.
- `_site_prices` and `_billing_url` now annotate `request: HttpRequest`, as `CLAUDE.md` asks for non-view helpers (from the reviewer's list of items over its cap).

Skipped:

- "The `team_id` fallback links a team to a customer from another environment that shares the Stripe account." True for worktrees that each run `stripe listen` against one test account, and for a test-mode production sharing it with development. Our own flow never needs the fallback: a Checkout session is only created once the team is linked to its customer, so subscriptions never land on an unlinked customer. The spec asks for the fallback. **Your call:** drop it, or add an environment tag to the metadata so that only this environment's customers match. Under Things you should know.
- "Teams keep their test customer and subscription when `STRIPE_LIVE_MODE` is switched." True. It is an operational step, written under Things you should know with the one-line unlink. Handling it in code would mean livemode checks in the guard, the customer lookup and `get_feature`.
- "`unpaid` and `paused` teams have no features and cannot subscribe again." They can open Manage billing, which the refusal message points to, and pay or cancel there. Once cancelled, they can subscribe again.
- "The team row lock is held during the Stripe call, and there is no idempotency key." The lock only blocks webhooks for a team that has no customer yet, and such a team gets none. A fixed idempotency key would make Stripe return the old customer for 24 hours, which would undo the purged-customer fix. An orphan customer from a rollback has no subscription and costs nothing.
- "Directory teams get a Billing tab and pages, against the anti-goal 'No directory billing'." The spec puts the views under `/a/<slug>/billing/` for team admins without naming a site. The directory page lists no plans, because no product has `metadata.site = directory`. 07-site-billing adds those products and the directory's portal configuration. Hiding the tab per site would mean site checks in the shared team templates.
- "`get_stripe_subscription` could be one query instead of up to five." A cleanup with no effect on correctness. It runs once per subscription webhook.
- "The WIP commits have no Verified list." They are squashed into the final commit, which carries the evidence.
