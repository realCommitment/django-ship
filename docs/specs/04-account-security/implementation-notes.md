# 04-account-security: implementation notes

## Decisions not in the spec

- **Dependency:** `django-allauth[mfa,socialaccount]>=65.13.0`. uv sorts the extras, so it reads `mfa,socialaccount`. The installed allauth stays at 65.19.1. The mfa extra brings `qrcode` 8.2 and also `fido2` 2.2.1, allauth's WebAuthn library. fido2 is installed but never used, because WebAuthn stays off.
- **No `MFA_*` settings.** allauth's defaults cover the spec: TOTP and recovery codes only (`MFA_SUPPORTED_TYPES`), 10 recovery codes of 8 digits, 6-digit codes every 30 seconds with no tolerance window, and "trust this browser" off. The QR code's issuer defaults to the current Site's name, taken from the request. An authenticator app therefore labels the entry "Productivity" or "Business Directory", depending on the site where 2FA was turned on. The comment on `"allauth.mfa"` in `INSTALLED_APPS` says the defaults are relied on.
- **`ACCOUNT_EMAIL_VERIFICATION` defaults to `"mandatory"` in `project/settings.py` for every environment**, and the env var can still override it. No Pegasus test had to change (64 pass), so the production-only fallback the spec allowed was not needed. I rewrote the comment above the setting to match.
- **Profile link:** `templates/account/components/profile_form.html`, one line under the profile form's Save button, "Two-factor authentication", linking to `{% url "mfa_index" %}`.
- **I fixed the two broken MFA pages in Pegasus's `templates/allauth/elements/` instead of under `templates/mfa/`.** Both breaks came from the shared element templates, not from the MFA templates. I checked them in a real browser (see Environment):
  - **`templates/allauth/elements/panel.html` (Pegasus's file):** the panel titles on the 2FA index ("Authenticator App", "Recovery Codes") came out empty. Pegasus wrapped `{% slot title %}` in `{% element h2 %}`. Inside an element block, a `slot` tag defines content for that element, so the title went to the h2's unused "title" slot and the h2 rendered blank. The fix is a plain `<h2>` with the same classes as Pegasus's h2 element, plus a one-line comment. The 2FA index is the only page that renders `element panel`, because Pegasus overrides every other allauth template that uses it. That is why the bug never showed until now.
  - **New `templates/allauth/elements/field.html`:** allauth's default `field` element has no CSS classes. On the activate page, "Authenticator secret" was a borderless input that cut the secret off partway through. On the recovery codes page, the label sat below an unstyled textarea. The override is allauth's own element with the classes Pegasus's `form_tags.py` uses: label `block mb-1 font-bold`, `input w-full`, `textarea w-full`, help text in `<small class="text-base-content/70">`, and checkbox and radio inputs inside their label. Overriding the two pages under `templates/mfa/` would have meant copying about 90 lines of allauth's page templates, which would then drift from allauth on every upgrade.
  - The 2FA prompt at login (`mfa/authenticate.html`) needed no change. Its Cancel button is styled as a primary button, because Pegasus's `button` element turns tags it does not know (here `link`) into `btn-primary`. I left that alone.
- **Tests:** `apps/users/tests/test_mfa.py` has 7 tests. They generate TOTP codes the way allauth's own `tests/apps/mfa/totp/test_unit.py` does: `format_hotp_value(hotp_value(secret, counter))` from `allauth.mfa.totp.internal.auth`, with `time.time` patched to a fixed timestamp. allauth's wheel ships no tests, so I read that file on GitHub. The helpers themselves come from the installed package. Users get TOTP and recovery codes through `TOTP.activate` and `RecoveryCodes.activate`, as allauth's `user_with_totp` and `user_with_recovery_codes` fixtures do. The wrong-code test sends the code from the previous 30-second step, which allauth's tolerance of 0 rejects.
- **The "password alone leads to the 2FA step" test runs on both site hosts**, because the spec says "on either site". Added after code review.
- **One test beyond the spec's four:** on both sites, the profile page links to `mfa_index` and that page returns 200 with "Authenticator App" in it. This covers the spec's URLs bullet ("Confirm the `mfa_index` route resolves on both site domains"). It also catches the panel bug: run against the old `panel.html`, it fails on both sites (checked).
- **The mandatory-verification test runs on the default setting, without `override_settings`.** It fails if the default ever changes. Checked: with `ACCOUNT_EMAIL_VERIFICATION=none` in the environment, `test_unverified_user_cannot_log_in` fails.

## Things you should know

- **Login by emailed code stays on** (Pegasus sets `ACCOUNT_LOGIN_BY_CODE_ENABLED = True`). An unverified user can still log in this way. allauth counts a correct emailed code as proof of the address and marks it verified, so 05-teams can still rely on a verified email. A user with TOTP who logs in by code still has to pass the 2FA step. I checked this against the running server: after the emailed code was accepted, the browser went to `/accounts/2fa/authenticate/` and was not logged in.
- **The profile's email change now asks for confirmation.** Under mandatory verification, `apps/users/views.py` (`require_email_confirmation()`) sends a confirmation email to the new address and keeps the old email until it is confirmed. Under `"none"` that code never ran. `ProfileEmailChangeTest` already covers it with `override_settings`.
- **Existing accounts with unverified addresses are locked out until they verify.** Their next password login redirects to "Verify Your E-mail Address", and allauth sends the link again. There is no production database yet, so nobody is affected today.
- **TOTP replay protection and allauth's rate limits depend on the cache.** In production that is Redis, so both work: a TOTP code cannot be used twice within its 30 seconds, and failed logins and repeated confirmation emails are rate-limited. Development and tests use `DummyCache` (`DEBUG` is on), so there a code can be reused within its window, and every blocked login re-sends the verification email. The end-to-end run showed this: two confirmation emails, one at signup and one at the blocked login. I did not exercise the replay protection.
- **MFA secrets are stored unencrypted.** allauth's default `MFAAdapter.encrypt` returns the text as it is, so the TOTP secret and the recovery-code seed sit in plain text in `mfa_authenticator.data`. allauth's `AuthenticatorAdmin` also shows `data` on its change page, so a staff user with view rights on "Authenticators" can read them too. Anyone with a database dump, or with that admin access, can generate a user's codes. **Your call:** encryption goes through `MFA_ADAPTER` (`encrypt`/`decrypt`). It needs a key and a cipher, and Django has no cipher built in, so it means a new dependency such as `cryptography`. Hiding `data` in the admin would need our own `ModelAdmin` for allauth's model. The spec asks for allauth's defaults, so I did neither.
- **A `createsuperuser` account cannot log in until its email is verified.** `/admin/login/` redirects to allauth's login (`project/urls.py`), and mandatory verification stops any user without a verified `EmailAddress` row. Such a user gets the verification email and gets in after clicking the link, which in production needs Postmark to work (03-go-live). Pegasus's own path still works without extra steps: sign up normally (which verifies the email), then run `manage.py promote_user_to_superuser <email>`. For a `createsuperuser` account, add a verified `EmailAddress` in `manage.py shell`.
- **A pending address blocks turning 2FA on.** allauth refuses to add an authenticator while the user has any unverified address (`validate_can_add_authenticator`), so that someone who signed up with another person's address cannot lock the real owner out. Pegasus's profile page adds an unverified address when the email is changed, so until that address is confirmed or removed, Activate on the 2FA page answers "You cannot activate two-factor authentication until you have verified your email address". The profile then shows "Manage email addresses", where the pending address can be removed. I kept allauth's rule (`MFA_ALLOW_UNVERIFIED_EMAIL` stays False).
- **The profile's email change does not check whether another account already uses the address** (`CustomUserChangeForm` has no uniqueness check, which predates this spec). Under `"none"`, the profile wrote that address straight into `CustomUser.email`. Under mandatory verification, it now adds an unverified address and sends a "confirm this address" email to whoever owns it. That owner cannot be taken over: allauth refuses to verify an address that another account has already verified. But a logged-in user can make the site send that email to any address. **Your call:** add a uniqueness check to the profile form. That changes what users can do on the profile page, so I did not.
- **No security notification emails** ("authenticator app activated" and the like). allauth sends them only when `ACCOUNT_EMAIL_NOTIFICATIONS = True`, and the spec does not ask for them.

## Code review

`/code-review medium`, with the django-ship repository and the range `cce08c8..HEAD` plus the working tree named in the arguments. All 14 findings were about django-ship files.

Fixed:

- "The login tests only use the productivity host." The password-then-2FA test now runs on both site hosts.

Skipped (the first three are under Things you should know, and **need your decision**):

- "TOTP secrets and recovery seeds are stored in plain text and shown in the admin." This needs a new dependency and our own admin for allauth's model, and the spec asks for allauth's defaults.
- "`createsuperuser` accounts can't log in until verified." This follows from the spec: every account has to verify its email. Pegasus's `promote_user_to_superuser` path works, and the notes give the shell step for `createsuperuser`.
- "The profile email change skips allauth's uniqueness checks." This predates the spec in Pegasus's profile view. Fixing it changes what users can do on the profile page.
- "A pending unverified address blocks turning 2FA on." This is allauth's deliberate protection, described in its docstring. Turning it off (`MFA_ALLOW_UNVERIFIED_EMAIL`) would weaken it.
- "DummyCache turns off rate limits and replay protection when DEBUG is on." The only deployment uses `settings_production`, which forces `DEBUG` off and uses Redis. Development is described under Things you should know.
- "Pegasus's layouts have no `extra_body` block, so `recovery_codes.js` is dropped." The script only adds click-to-select-and-copy on the codes textarea, plus a leave-page warning for `MFA_RECOVERY_CODES_SHOW_ONCE`, which is off. The codes can still be selected by hand, and "Download codes" works (used in the end-to-end run). Adding the block means editing Pegasus's layouts.
- "The 2FA prompt's Cancel button looks like Sign In." A styling point about Pegasus's button element. Cancel does what it says: it ends the half-finished login.
- "The TOTP issuer depends on the site where 2FA was turned on." A fixed issuer would have to be one brand for every site, and the product spec says visitors never notice the shared backend. The code works on every site whatever the label says.
- "The verification test depends on the env default." On purpose: it guards the spec's default. CI, a fresh checkout and `.env.example` do not set the variable.
- "The WIP commits have no Verified list." They are squashed into the final commit, which carries the evidence.
- "panel.html is edited and field.html added, instead of overrides under `templates/mfa/`." Explained under Decisions: the breaks were in the shared elements, and the alternative copies about 90 lines of allauth's templates.
- "field.html copies Pegasus's form classes." Pegasus's own `form_tags.py` and widget templates repeat the same classes as literals. It is the house pattern.
- "fido2 is installed but unused." The spec names the `mfa` extra, which pulls fido2 in.

## Environment

- **`make` is not installed on this machine.** I ran the Makefile recipes directly through `~/.local/bin/mise exec --`: `make test` is `uv run manage.py test`, and `make type-check` is `uv run mypy .`.
- **No Playwright MCP was available.** I drove spec steps 2 to 4 in a real browser instead: headless Chromium 155 (snap), controlled through the Chrome DevTools Protocol by a small Node script. Node 24 has a built-in WebSocket, so this added no dependency. The script lives in the session scratchpad and is not committed. The Vite dev server ran next to `runserver`, so the pages had their CSS in the screenshots. I computed TOTP codes from the secret shown on the activate page with allauth's helper in `manage.py shell -c`.
- **`manage.py check --deploy` under production settings** ran in a `git archive HEAD` export, as 01-production's notes describe: mise puts the checkout's `.env` `SECRET_KEY` back. The built Vite manifest was copied in from the checkout, because the export has no front-end build.
