# 05-teams: implementation notes

## Decisions not in the spec

- **Create-team URL is `teams/new/`, not under `a/`.** `a/new/` would make a team with the slug `new` unreachable. The form asks only for a name; the slug is `slugify(name)`, cut to 90 characters, with `-2`, `-3` and so on when the site already has it (`team` if the name has no sluggable characters). Two teams with the same name created at the same instant can race to one slug; the unique constraint then answers 500 and nothing is saved. That is marked as a `shortcut:` comment in `create_team`.
- **Who sees what on team URLs:** a logged-out visitor is sent to login (302, `login_required`), as everywhere else in the app. A logged-in user who is not a member, or who is on the other site, gets 404. A member who is not an admin gets 403 on admin-only URLs (they already know the team exists). The URL matrix test pins all of this.
- **The wrong-site check is the lookup, not a validation code.** The invitation view looks the token up with `team__site=request.site`, so another site's token is a plain 404, for GET and POST. The other checks are `Invitation.validate()` codes: `expired`, `already_member`, `email_mismatch`, in that order. `accept()` re-reads the row under `select_for_update()` through `open()`; a row that was accepted in the meantime raises "This invitation has already been used." with code `expired`, as PostHog's `InviteExpiredException` does.
- **An accepted invitation cannot be used again.** The view only finds open invitations, so an old link answers 404 after it was accepted, even if the person has since left or been removed. The re-read under the lock covers the same case for a request that loaded the row before another one accepted it.
- **Resending:** inviting an address that has a live open invitation sends nothing and says "already has a pending invitation" (the spec's no-duplicate rule). Inviting it again after the invitation expired resends it: `sent_at` is bumped, the role and `invited_by` become the ones of this request, and the email goes out again. This is the only place `sent_at` is bumped; there is no separate Resend button. The members page marks expired pending invitations, so an admin can see when re-inviting will resend.
- **No decline action for the invitee.** The spec's user actions do not list one. Read the Docs' "decline/revoke" test shape is covered by the admin's revoke.
- **The adapter lives in the teams app.** `apps/teams/adapter.py` has `TeamInvitationAdapter`, a subclass of Pegasus's `EmailAsUsernameAdapter`, and `ACCOUNT_ADAPTER` points at it. Pegasus's `apps/users/adapter.py` is unchanged, so upstream merges stay easy and the users app does not depend on teams. (The first version edited Pegasus's adapter; moved after code review.)
- **Landing in the team after signup.** The anonymous-without-account branch stores the invitation id in the session (`invitation:pk`) and redirects to signup without `next`. `TeamInvitationAdapter.confirm_email` pops that id after allauth verifies the address and calls `invitation.accept(user)`, which runs the same checks as the view (so the verified email must match). On success it stores the team URL in the session, and `get_signup_redirect_url` pops it, so allauth's login-on-confirmation lands the person on `/a/<slug>/`. On failure (signed up with another address, expired, revoked) an error message is shown and the person lands on the dashboard. A `next` to the team URL would have sent a failed redemption to a 404.
- **That redemption needs the same browser.** The invitation id is in the signup session, as is allauth's own login-on-confirmation. If the confirmation link is opened elsewhere, the person logs in, opens the invitation link again and accepts with one click.
- **Expired invitation, logged out:** the page shows the expiry message instead of sending the visitor to login or signup.
- **"Has an account" uses allauth's `filter_users_by_email`** (EmailAddress rows, then `User.email`). It tells whoever holds the token whether the invited address has an account; the token holder is the invitee.
- **The email is queued with `transaction.on_commit`**, so the worker never looks for a row that is not committed yet. If the invitation was revoked (or accepted) before the worker runs, the task logs the invitation id at INFO and sends nothing. The subject is joined onto one line, as allauth does, so a line break in a team name cannot make every invitation email for that team fail. The task gets the invitation id only and reads everything from `invitation.team.site`: `site_key_for()` gives the `SITES` entry (sender, label, urlconf for `reverse`), the scheme comes from Pegasus's `get_protocol()` (`USE_HTTPS_IN_ABSOLUTE_URLS`, https in production), and the host is `Site.domain`. Subject `[<site name>] You're invited to join <team>`, a text part and an HTML part on Pegasus's email base template.
- **Locking in `validate_role_change`.** It locks the team row (`select_for_update`), then re-reads both the actor's and the target's role and decides on those, so two admins demoting each other at the same moment cannot both pass the count and leave the team with none, and an admin demoted a moment ago cannot finish a role change that was waiting on the lock. If either membership is gone by then (a double-clicked Remove or Leave), it raises code `not_member` and the view shows a message instead of a 500. It must run inside `transaction.atomic()` together with the change; outside a transaction `select_for_update` raises, so misuse is loud. The admin count is `Membership.objects.filter(team=...).admins().count()`.
- **Revoking locks the invitation row** (`select_for_update` on the open invitation), so a revoke that races an accept waits for it, then finds the invitation no longer open and answers 404 instead of deleting the accepted record.
- **On-delete choices:** `Team.site` is `PROTECT` (deleting a Site row in the admin would otherwise delete every team on it), `Invitation.invited_by` is `SET_NULL`, memberships and invitations cascade with their team, memberships cascade with their user.
- **Team switcher and label through a context processor** (`apps.teams.context_processors.teams`, one line in `TEMPLATES`): `team_label` for every page, and `user_teams` as a lazy queryset for logged-in users, so only pages that render the nav run the query. Pegasus's `app_nav_menu_items.html` got one include (`teams/components/team_nav.html`), as the spec asks. The section title is the label ("Business" / "Team"), each team links to `/a/<slug>/`, and "New business" / "New team" links to the create form.
- **`TEAM_INVITATION_EXPIRY_DAYS = 14`** is a plain setting, not an env var; the spec only asks for a setting with that default.
- **Pages:** team home (`/a/<slug>/`, name, label and your role), members (`/a/<slug>/members/`: every member sees the list and a Leave button; admins also get a role select with "Change role", Remove for others, the pending invitations with Revoke, and an "Invite someone" button), the invite form on its own page (`/a/<slug>/members/invite/`), and the invitation page. Plain POST forms with redirects; nothing needed HTMX. An admin has no Remove button on their own row (Leave does that); the remove URL still goes through the guard.
- **Wording avoids "a admin":** roles are shown as "with the role Admin" / "Your role: Admin".
- **The invite form does not check whether the address already belongs to a member.** Accepting such an invitation answers "already a member". Not in the spec.
- **`site_key_for(site)` raises `KeyError`** for a row no `SITES` entry has. The middleware still catches `KeyError` and redirects, as before.
- **Source comments** name Keel (model shape, the decorators), Read the Docs (`open()`/`expired()` naming, `get_or_create` invite, the invitation view shape, redeem at signup, the last-owner guard) and PostHog (role levels, validation codes, the row lock), all MIT.

## Things you should know

- **In development the invitation link has no port.** It is built from `Site.domain`, as the spec says, so the console email reads `http://directory.localhost/invitations/<token>/`. The end-to-end run added `:38697` by hand. In production the domain is the real one and the scheme is https. 02-sites has the same note about the sitemap.
- **If the broker is down when an admin invites someone**, the invitation row is saved and the request answers 500 when `.delay()` fails. Inviting the same address again then says "already has a pending invitation" and sends nothing until it expires. The admin can revoke and invite again. I left it loud rather than catching the error.
- **Messages say "team" on every site.** The last-admin refusal reads "Every team needs an admin" on the directory too, where teams are called businesses. The page labels use the site's label; the validation messages come from the model, which has no request.
- **The test output now shows `PermissionDenied` tracebacks.** Django logs every 403 with its traceback at WARNING; the URL matrix and the revoke test hit 403 on purpose. The suite still passes.
- **The double-POST test is sequential.** The second POST gets 404, because an accepted invitation is no longer open. The lock itself is exercised by accepting a stale copy of an invitation that was already used. A real concurrent test would need threads in a `TransactionTestCase`.

- **Pegasus files touched:** `project/settings.py` (`apps.teams` in `INSTALLED_APPS`, the context processor, `ACCOUNT_ADAPTER`, `team_label` in `SITES`, `TEAM_INVITATION_EXPIRY_DAYS`), `project/urls.py` (one include of `apps.teams.urls` in the shared routes) and `templates/web/components/app_nav_menu_items.html` (one include). `apps/multisite/middleware.py` (ours) now calls `site_key_for()`.
- **Dev database:** `teams.0001_initial` is applied. The end-to-end users `a@example.com` and `b@example.com` and their business were deleted afterwards; the dev database has the same 3 users and no teams, as before the session.

## Code review

`/code-review medium`, with the django-ship repository and the range `05eaf23..HEAD` plus the working tree named in the arguments. All 15 findings were about django-ship files.

Fixed:

- `validate_role_change` re-read the target with `refresh_from_db()` after the lock, so a target deleted meanwhile (a double-clicked Remove or Leave) raised `DoesNotExist` and a 500. It now reads both rows after the lock and raises a `not_member` ValidationError. Test: `test_decisions_use_the_rows_as_they_are_under_the_lock`.
- The actor's admin check used the object the decorator loaded before the lock, so an admin demoted a moment ago could still finish a waiting change. The check now uses the actor's role read under the lock. Same test.
- Revoke could delete an invitation that a concurrent accept had just accepted. It now locks the open row first (see Decisions).
- A line break in a team name put a newline in the email subject, which `send_mail` rejects. The subject is now joined onto one line. Test: `test_subject_stays_on_one_line`.
- Resending an expired invitation kept the original `invited_by`, so the email could name a former admin or nobody. It now records the admin who resent it. Covered in `test_inviting_again_after_expiry_resends_with_a_new_expiry`.
- The task raised a bare `DoesNotExist` with no id when an invitation was revoked before the worker ran. It now logs the id and sends nothing, because there is nothing to send. Test: `test_revoked_invitation_sends_nothing`.
- `create_team` did not pass `active_tab`, so "New business" was never highlighted in the nav.
- The team code lived in Pegasus's `apps/users/adapter.py`. It now lives in `apps/teams/adapter.py` (see Decisions).

Skipped:

- "Open invitations stay valid after the inviting admin is demoted or removed; a removed admin could have pre-invited a second address of theirs as Admin." Real, but Read the Docs and PostHog behave the same way, and the remaining admins see every pending invitation, each with a Revoke button, on the members page. Checking the inviter's current role when accepting would also cancel harmless invitations from admins who left. **Your call** if you want that check, or pending invitations revoked when their inviter leaves or is demoted.
- "Redemption only works when the confirmation link is opened in the same browser." That follows from the spec ("store the invitation id in the session"), and allauth's own login-on-confirmation has the same limit. Under Decisions. The finding's side note, that with `ACCOUNT_EMAIL_VERIFICATION=optional` the joined-team key can stay in the session, applies only to a setting this project does not use (verification is mandatory).
- "If the broker is down, the invitation is saved and the admin cannot resend it until it expires." Under Things you should know; the 500 is loud, and revoke plus a new invite works.
- "The invitation link has no port in development." The spec says to build it from `Site.domain`. Under Things you should know.
- "`validate_role_change` should be `Membership.change_role()` / `remove()` methods that lock, check and write in one place." The spec names `validate_role_change()`. With the re-reads under the lock, the two races the finding derived from this split are fixed.
- "The decorator runs two queries where one would do." The spec gives the team lookup word for word. One query per team page.
- "The WIP commits have no Verified list." They are squashed into the final commit, which carries the evidence.

## Environment

- **A stale `test_project` database blocked one test run.** The code-review run had left one behind, and `manage.py test` stopped at its "delete the old test database?" prompt with no terminal to answer it. I re-ran with `--noinput`, which deleted it; every later run passed.

- **`make` is not installed on this machine.** I ran the Makefile recipes directly through `~/.local/bin/mise exec --`: `make test` is `uv run manage.py test`, and `make type-check` is `uv run mypy .`.
- **No Playwright MCP.** I drove the end-to-end steps with a Python `requests` script (one cookie jar per person, CSRF tokens from the forms) against the real `http://directory.localhost:38697` and `http://productivity.localhost:38697`, with `runserver` and a real Celery worker (`celery -A project worker --pool solo`). No browser was started, so there are no screenshots; the captures are the status codes, final URLs, flash messages and page text. Vite was not running, so the pages had no CSS.
