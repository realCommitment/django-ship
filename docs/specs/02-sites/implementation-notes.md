# 02-sites: implementation notes

## Decisions not in the spec

- **"Unknown domain" also covers a Site row that is not in `SITES`.** The middleware redirects when `Site.objects.get_current(request)` finds no row, and also when it finds a row whose domain no `SITES` entry has. Settings are the source of truth, and every database already holds one such row: the first Site that Pegasus's `apps/web/migrations/0001_initial.py` creates from `PROJECT_URL` (`localhost:8000` here). Without this, a request for that host would get a `request.site` with no site key and fail in the context processor.
- **The redirect keeps the query string** (`request.get_full_path()`), as well as the scheme and port. `/some/path?page=2` on an unknown host goes to `http://productivity.localhost:<port>/some/path?page=2`.
- **If a configured domain (any `SITES` entry) has no Site row, the middleware raises `ImproperlyConfigured` ("Run manage.py sync_sites") instead of redirecting.** For the main site, a redirect would loop forever. For the other sites, it would quietly show the main site in their place. This happens when `sync_sites` has not run after `migrate`. Domains are compared lowercased, so an uppercase letter in a domain env value cannot slip past the check and loop.
- **The health check bypass compares `request.path_info == "/health/"`**, hard-coded like `SECURE_REDIRECT_EXEMPT` in the production settings.
- **Pegasus's `apps/web/migrations/0001_initial.py` reads `id=1` instead of `settings.SITE_ID`.** With `SITE_ID` gone, a fresh database (every test run, every new worktree) crashed in that migration. It still creates the first Site row from `PROJECT_URL`, which no site uses. I kept the row rather than turning the migration into a no-op: with no rows at all, Django's own `post_migrate` handler creates an `example.com` row anyway. The `.env.example` comment on `PROJECT_URL` now says this.
- **`sync_sites` keys rows on the domain, case-insensitively** (`update_or_create(domain__iexact=..., defaults={"domain": ..., "name": ...})`), the same way Django's request lookup matches. An exact match would let a second row differ only in case, and every request to that site would then raise `MultipleObjectsReturned`. The name, and the domain's case, are updated in place. Changing a domain in an environment that already has data creates a new row and leaves the old one, along with any `SignupSite` rows that point at it. `sync_sites` never deletes rows: that would null `SignupSite.site` and drop allauth social-app links. See Things you should know.
- **The context processor wraps Pegasus's `project_meta`.** `apps/multisite/context_processors.py` calls it, then replaces `NAME`, `DESCRIPTION`, `KEYWORDS`, `IMAGE` and `URL` with the current site's values, recomputes `TITLE` the same way Pegasus does, and adds `GOOGLE_ANALYTICS_ID`. Pegasus's `project_meta` changed in two lines only: it passes the request to `get_server_root` and `absolute_url`. `URL` is the request's scheme and host (`server_url`), so it includes the dev port.
- **Analytics is per site only.** The global `GOOGLE_ANALYTICS_ID` setting is removed, and so is Pegasus's `google_analytics_id` context processor (its line in `TEMPLATES` and the function in `apps/web/context_processors.py`, which mypy rejected once the setting was gone). Otherwise a global ID set in the environment would override the site's ID. The env keys are `DIRECTORY_GOOGLE_ANALYTICS_ID` and `PRODUCTIVITY_GOOGLE_ANALYTICS_ID`. The checkout's `.env` still has `GOOGLE_ANALYTICS_ID=""`, which is now ignored; I did not edit `.env`.
- **Env names and defaults for senders:** `DIRECTORY_FROM_EMAIL` and `PRODUCTIVITY_FROM_EMAIL`, defaulting to `hello@directory.localhost` and `hello@productivity.localhost`. The two defaults differ so that each site's emails are recognisable locally and the per-site test means something.
- **Placeholder site names:** "Business Directory" ("Find and compare local businesses.") and "Productivity" ("Plan your work and get it done."), with matching keywords. Landing headlines: "Find the right local business" and "Get your work done".
- **`image` must be an absolute URL.** The `get_image_url` filter in `base.html` has no request. A relative static or media path would make it call `absolute_url` without one, which raises (no `SITE_ID`). The settings comment says so. `base.html` leaves `og:image` and `twitter:image` out when the image is empty (`{% if image %}` around the two tags), as the spec asks. Before this change they were rendered with an empty `content`.
- **`get_server_root(request=...)` uses `request.build_absolute_uri("/")` and ignores `is_secure`.** The scheme comes from the request, which honours `SECURE_PROXY_SSL_HEADER` in production. Without a request it still calls `Site.objects.get_current()`, which now raises `ImproperlyConfigured`. That is fail-loud, and the signatures stay compatible with upstream. `apps/web/tests/test_meta.py` now passes requests, and asserts that a call without one raises.
- **The `absolute_url` template tag takes the context** and passes `context.get("request")`. No template uses it today.
- **Site templates live in project-level `templates/<site>/`**, as `pegasus startapp` lays them out, not inside the app directories.
- **robots.txt:** each site has `templates/<site>/robots.txt`, which includes Pegasus's `robots.txt` and adds `Sitemap: {{ server_url }}/sitemap.xml`, so the line carries the request's scheme, host and port.
- **sitemap.xml:** each site's `urls.py` has a small `StaticViewSitemap` subclass listing that site's `home`. Django's sitemap view builds `<loc>` from `Site.domain`, which has no port. In dev the URLs read `http://directory.localhost/` without `:38697`. In production they are correct.
- **`sync_sites` also runs from the Makefile's `migrate` target** (which `make init` uses), besides the two scripts the spec names. `CLAUDE.md` documents `make init` and `make migrate` as setup. Without it, a database set up that way has no site rows, and every page answers 500.
- **Production requires each site's domain and sender.** `settings_production.py` reads `DIRECTORY_DOMAIN`, `DIRECTORY_FROM_EMAIL`, `PRODUCTIVITY_DOMAIN` and `PRODUCTIVITY_FROM_EMAIL` with no default. This is the pattern 00-saas-layer used for `DEFAULT_FROM_EMAIL`, and it follows the fail-loud rule. Without them, production would quietly serve the `*.localhost` defaults: every real request would redirect to `productivity.localhost`, and email would go out from `hello@*.localhost`. Both services in `render.yaml` get the four keys as `sync: false` prompts, as 01-production did for the other required keys, and CI's production check sets example values. Running the production settings locally now needs these four keys too, on top of the three in 01-production's notes. Added after code review.
- **The site home views delegate logged-in users to `apps.web.views.home`**, so the dashboard code stays in one place.
- **`apps.multisite`, `apps.directory` and `apps.productivity` are in `INSTALLED_APPS`.** Only multisite has an `apps.py` (it connects the signal in `ready()`, label `multisite`). The site apps have no models yet.
- **The signup site is recorded in `apps/multisite/signals.py`** (`user_signed_up` → `SignupSite.objects.create(user=user, site=request.site)`). No admin page for `SignupSite`; the spec asks for none.
- **Tests get Site rows from `SiteTestCase`** (`apps/multisite/tests/base.py`): `setUpTestData` runs `sync_sites`, and `setUp` points `self.client` at the main site's host. `site_client(key)` gives a client for any site. Pegasus's `TestViewBase`, `TestApiSchema` and `ProfileEmailChangeTest` now extend it, and `TestLoginRequiredViewBase`'s authenticated client gets the host. I considered two global options and rejected both. A custom test runner that syncs after `setup_databases` misses the clones `--parallel` makes inside that call. A `post_migrate` handler would make the explicit `sync_sites` the spec puts in the scripts redundant.
- **`SiteTestCase` clears Django's `SITE_CACHE`.** The cache is per process and keyed by domain. A later test class otherwise got a Site object whose row an earlier class had rolled back, and signup failed with a foreign-key `IntegrityError`. I confirmed this by removing the line and running `apps.multisite --reverse` (2 errors).
- **`request.site_key` needs `# type: ignore[attr-defined]`** where it is set and read (middleware, context processor). django-stubs declares `site` and `urlconf` on `HttpRequest`, but not `site_key`. In the adapter, `allauth.core.context` is untyped, so nothing is needed there.
- **Source comment:** the middleware's docstring names envergo's `SetUrlConfBasedOnSite`, MIT, "Copyright (c) 2021, MTES". The code follows its shape; nothing was copied verbatim.

## Things you should know

- **03-go-live fills in the four new Render prompts** (`DIRECTORY_DOMAIN`, `PRODUCTIVITY_DOMAIN`, `DIRECTORY_FROM_EMAIL`, `PRODUCTIVITY_FROM_EMAIL`) on both services. Without them neither service starts. Each domain also has to go into `ALLOWED_HOSTS`.
- **Set each environment's domains before its first `sync_sites`.** Because rows are keyed on the domain, changing a domain later leaves the old row (and its signups) behind. To move a site to a new domain, change `domain` on the existing Site row in the admin or shell, then the env value.
- **The onrender.com hostname will redirect to the main site** (apart from `/health/`). Hosts outside `ALLOWED_HOSTS` never reach the redirect: Django answers 400 when the middleware calls `get_host()`.
- **Emails sent without a request now fail loudly.** `ACCOUNT_EMAIL_SUBJECT_PREFIX = None` makes allauth look up the Site from the request, and there is no `SITE_ID` to fall back on. No such email exists today. Celery tasks that send email must take a `site_id` (the rule is in `CLAUDE.md`).
- **The admin signup notification is not per site.** Pegasus's `mail_admins` email still reads "[django-ship] Yowsers, someone signed up for django-ship!". It goes to admins, not visitors.

## Code review

`/code-review medium`, with the django-ship repository and the range `513795d..HEAD` plus the working tree named in the arguments. All 15 findings were about django-ship files.

Fixed:

- The `*.localhost` domain and sender defaults applied in production. They are now required there, with `render.yaml` prompts and CI values (see Decisions).
- A configured site with no Site row was quietly redirected to the main site. It now raises for every configured domain, compared lowercased, which also covers the finding that an uppercase main domain looped.
- `make init` and `make migrate` did not run `sync_sites`. The Makefile's `migrate` target now runs it.
- `sync_sites` matched domains case-sensitively, so a row that differed only in case got a duplicate, and every request to that site then raised `MultipleObjectsReturned`. It now matches with `iexact`, and a test covers it.
- `SiteTestCase` cleared the site cache only when a class started. It now also clears it when the class ends (`addClassCleanup`), so a later plain `TestCase` cannot get a rolled-back Site object.

Skipped:

- "The `get_image_url` filter calls `absolute_url` without a request, so a relative image raises." No caller passes a relative image: both sites' `image` is empty and no view sets `page_image`. The failure is loud, and the settings comment says the image must be absolute. Fixing it means turning the filter into a context-taking tag in `base.html`. The spec names only the context processor and the `absolute_url` tag as callers that pass the request.
- "`SITE_CACHE` grows with every case variant of the Host header." That is how Django's `Site.objects.get_current(request)` caches, and allauth and the sitemap view call it as well, so working around it in the middleware would not close the gap. Bounded by what `ALLOWED_HOSTS` lets through in production. **Your call** if you want the host lowercased before any lookup.
- "A domain with a port gets a double port in the redirect." Domains are hostnames by spec. A port in `*_DOMAIN` is a misconfiguration.
- "Key Site rows on a stable id instead of the domain." The spec defines `sync_sites` by domain and name, and there is no production database yet. Under Things you should know: set the domains before the first `sync_sites`. **Your call** if you want stable ids in `SITES` before 03-go-live.
- "`record_signup_site` raises `AttributeError` when the request did not pass through the middleware." Every real signup is an HTTP request through the middleware, allauth headless included. Any other caller is a programming error, and the error is loud.
- "`is_secure` is ignored when a request is passed." The spec says `server_url` and `page_url` come from the request. In production the request's scheme is https through `SECURE_PROXY_SSL_HEADER`.
- "The two site apps duplicate each other." The spec gives each site its own `urls.py`, home view, robots.txt and sitemap. They are the places where the sites will diverge.
- "The domain-to-key dict is rebuilt on every request." It has two entries. Building it per request keeps `override_settings(SITES=...)` working.
- "The adapter's `DEFAULT_FROM_EMAIL` fallback is unreachable while `ACCOUNT_EMAIL_SUBJECT_PREFIX = None`, because `format_email_subject` raises first without a request." True. The spec asks for both settings. The fallback starts to matter if the prefix ever becomes a fixed string.
- "The WIP commit has no Verified list." It is squashed into the final commit, which carries the evidence.

## Review follow-up (orchestrating session)

- The middleware lowercases `HTTP_HOST` before any site lookup. Django's `SITE_CACHE` is keyed by the raw Host string, so case variants of a real domain each added an entry in every worker. New test `test_host_case_is_normalised_before_the_site_lookup` fails without the change and passes with it. It reads `SITE_CACHE` through the module because `Site.objects.clear_cache()` rebinds it.
- Decision on Site rows matched by domain: accepted as is. Each environment's domains must be set before its first `sync_sites`. On Render, `render.yaml` prompts for `DIRECTORY_DOMAIN` and `PRODUCTIVITY_DOMAIN` at Blueprint creation, before the first `pre_deploy.sh` runs.
