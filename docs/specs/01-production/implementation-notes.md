# 01-production: implementation notes

## Decisions not in the spec

- **Production settings force `DEBUG` off before `settings.py` loads** (`os.environ["DEBUG"] = "False"` above `from .settings import *`). `settings.py` decides several things from `DEBUG` at import time: the Vite dev server (`DJANGO_VITE` `dev_mode`), `django_browser_reload` in `INSTALLED_APPS` and `MIDDLEWARE`, the cached template loader and the dummy cache. `DEBUG` defaults to True there, so without this the spec's local commands served pages that load assets from the Vite dev server. On Render it would crash at import, because `django_browser_reload` is a dev dependency and `uv sync --no-dev` leaves it out. The alternative was a required `DEBUG=False` env var in every place that loads production settings; forcing it in the production module cannot be forgotten. `settings.py` is unchanged.
- **gunicorn moved into the main dependencies** (`uv add gunicorn`). It was only in Pegasus's `prod` group, and the spec's `uv sync --frozen --no-dev` installs no groups, so Render would have had no gunicorn. I did not use `--group prod` because that group also holds `psycopg[c]`, which compiles against libpq headers; that is possible on Render (see below), but nothing needs it. Pegasus's `prod` group is left as it was, so it still lists gunicorn too. With gunicorn in the main group the spec's `uv run gunicorn ...` works locally as written.
- **`ALLOWED_HOSTS` defaults to an empty list in production, not required.** The spec lists it with the required keys for CI but also says the worker gets "the same env as the web service minus `ALLOWED_HOSTS`". If it were required, the worker would crash on import. An empty list is still loud on the web service: `check --deploy` fails with `security.W020` (checked, see the commit), and every request gets a 400. On Render the web service always has `RENDER_EXTERNAL_HOSTNAME`, so it serves its onrender.com address before 03-go-live adds domains.
- **The required sender and admin keys are in `render.yaml`.** `ADMINS`, `DEFAULT_FROM_EMAIL` and `SERVER_EMAIL` are required at import, so both services get them as `sync: false` prompts next to the spec's placeholders. Without them neither service would start. They cannot go in the env group: Render ignores `sync: false` inside env groups (Blueprint spec), so each service lists its own prompts.
- **The spec's local commands need three more env vars.** `ADMINS`, `DEFAULT_FROM_EMAIL` and `SERVER_EMAIL` are required in production (00-saas-layer and this spec), and the dev `.env` does not set them. Every production command in the commit passes them inline.
- **Optional keys treat an empty value as unset** (`env(..., default=None)` and a truthiness check), for `RENDER_EXTERNAL_HOSTNAME`, `AWS_STORAGE_BUCKET_NAME`, `POSTMARK_SERVER_TOKEN` and `SENTRY_DSN`. A `sync: false` prompt left blank on Render then turns the feature off instead of failing on an empty bucket name or DSN.
- **Postmark token:** `ANYMAIL` only gets `POSTMARK_SERVER_TOKEN` when it is set. Without it, the first send raises `AnymailConfigurationError` ("You must set ANYMAIL = {'POSTMARK_SERVER_TOKEN': ...}"), checked under production settings. A `None` value would have been sent to Postmark as a missing token. The variable holding it is lowercase on purpose: an uppercase module name is a Django setting, and anymail would read a `None` `POSTMARK_SERVER_TOKEN` setting as the token.
- **R2 settings:** when `AWS_STORAGE_BUCKET_NAME` is set, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_S3_ENDPOINT_URL` become required (checked: a missing key raises `ImproperlyConfigured`). `AWS_S3_CUSTOM_DOMAIN` stays optional. From cookiecutter I kept `file_overwrite = False` as `AWS_S3_FILE_OVERWRITE` (an upload with an existing name gets a new name instead of replacing someone else's file). I left out cookiecutter's `AWS_QUERYSTRING_AUTH = False`: R2's S3 endpoint refuses unsigned reads, so without a public custom domain the URLs must stay signed. With a custom domain django-storages builds plain URLs anyway. Also left out: `location`, the cache-control and max-memory options, `MEDIA_URL`, `"storages"` in `INSTALLED_APPS`. None of them are needed for R2.
- **Sentry:** `environment` comes from `SENTRY_ENVIRONMENT` and defaults to `production`, as in cookiecutter. It is a label, so a default hides no error. cookiecutter's logging and Redis integrations and its trace sampling are left out; the spec asks for Django and Celery.
- **Health check:** the 503 body is `{"status": "error", "failed_check": "database"}`. It catches `django.db.Error`, the base of every database error including `InterfaceError`, and logs the exception with the `apps` logger before answering.
- **API schema test:** the existing "schema returns 200" test now logs in a staff user, so schema generation stays covered. The new anonymous test checks all three URLs for 403. Generating the TypeScript client still works with `manage.py spectacular --file`, which does not go through the view.
- **Running commands on Render:** `render.yaml` and the deploy scripts call `.venv/bin/gunicorn`, `.venv/bin/celery` and `.venv/bin/python`. Render's docs say uv is added to the runtime when `uv.lock` exists, but not whether it is on PATH at start time. `uv run` would also re-sync the dev group. The commands assume `uv sync` creates `.venv` in the repo root, which is uv's default; Render's docs do not say where the venv goes.
- **gunicorn bind:** `--bind 0.0.0.0:$PORT` is spelled out, although gunicorn reads `$PORT` by itself.
- **Worker deploys also wait for CI** (`autoDeployTrigger: checksPass` on the worker too). The spec names it only for the web service, but the product spec deploys "on every green push", and a worker that deploys on every commit would run code CI has not passed.
- **Region `oregon`**, Render's default, on all four resources, with a comment at the top of `render.yaml`. **Your call:** the spec gives no region, and moving later means recreating the database. Frankfurt is the EU option.
- **`CONN_HEALTH_CHECKS = True`** next to the spec's `CONN_MAX_AGE`. Without it, after a Postgres restart, the first request on each gunicorn worker reuses the dead persistent connection and fails with a 500. Added after code review.
- **Database:** `basic-256mb` (the smallest paid plan), `postgresMajorVersion: "17"` to match `docker-compose.yml` and CI. `databaseName` and `user` are left to Render.
- **`ipAllowList: []` on the database and Key Value**: no access from the public internet, only from Render's private network. The schema requires `ipAllowList` on Key Value. A database without it accepts connections from any IP (Render's default).
- **CI dummy `SECRET_KEY`** is 60 characters with many unique characters, so `check --deploy` does not raise `security.W009` for a weak key. The spec's `local-prod-check` would fail that check; it is fine for gunicorn, which does not run deploy checks.
- **`.env.example`** documents `SENTRY_ENVIRONMENT` and `AWS_S3_CUSTOM_DOMAIN` along with the keys the spec lists, because the settings read them.
- **Source comment:** one line in `settings_production.py` names cookiecutter-django, its copyright holder (Daniel Roy Greenfeld) and BSD-3-Clause.

## Things you should know

- **Render's health check and `ALLOWED_HOSTS` (03-go-live risk).** `/health/` goes through Django's host check like every other request. Render does not document the `Host` header its health check sends. Community threads report `Host: localhost:10000` coming from Render's port detector, and Render staff suggested adding `localhost` to `ALLOWED_HOSTS`. I did not add it, because the spec defines the host list. If the first deploy in 03-go-live never turns healthy, look here first.
- **Celery concurrency on Render.** The spec's worker command has no `--concurrency`, so Celery starts one process per CPU it can see. Locally that was 8 (`concurrency: 8 (prefork)`). On a 512 MB starter instance that may run out of memory if Render shows the host's CPU count. If it does, add `--concurrency 2` to the worker's `startCommand`.
- **libpq on Render.** The main group installs only pure-Python `psycopg`, which loads the system libpq. This machine has no system libpq. Running `deploy/build.sh` in a clean export got through `uv sync --frozen --no-dev`, `npm ci` and `npm run build`, then collectstatic failed with "libpq library not found". After `psycopg[binary]` was added to that export's venv only, collectstatic, `pre_deploy.sh` and `.venv/bin/gunicorn` all worked. Render lists `postgresql-client` as installed, and its own Django guide installs `psycopg2` from source, which needs libpq, so libpq should be there. If it is not, add `psycopg[binary]` to the main dependencies.
- **Node version on Render** is not pinned. Locally Vite 8 builds on Node 24 (mise). If Render's default Node is too old for Vite 8, set `NODE_VERSION` in `render.yaml`.
- **The API docs are staff-only in development too.** That follows from the spec putting `permission_classes` in `project/urls.py`. `GET /api/schema/` on the dev server is now 403 for anonymous users.
- **Static cache headers:** with plain `CompressedStaticFilesStorage`, whitenoise sends `Cache-Control: max-age=60` for every file, Vite's hashed chunks included. A `WHITENOISE_IMMUTABLE_FILE_TEST` for the hashed names would let browsers keep them for good. Not done; the spec does not ask for it.
- **`pre_deploy.sh` was run against the dev database** to prove the script works. `migrate` had nothing to apply, and `bootstrap_celery_tasks` created the `clear-expired-sessions-every-day` periodic task there.

## Code review

`/code-review medium`, with the django-ship path and the range `6b8e58e..HEAD` named in the arguments. All ten findings were about django-ship files.

Fixed:

- Persistent connections had no health check (`CONN_HEALTH_CHECKS`, see above).
- Also fixed, though not a review finding: ruff's `PLW1510` flagged the settings test's `subprocess.run` on a later pre-commit run (an earlier run had passed), so the call now passes `check=False` explicitly.

Skipped:

- "`plan: 256mb` is not a valid Key Value plan." It is. Render's published Blueprint schema (`https://render.com/schema/render.yaml.json`) lists `256mb` in `keyValuePlan`, and `render.yaml` validates against that schema with 0 errors.
- "The worker can deploy before the web service's `preDeployCommand` has migrated." This is real: both services deploy when checks pass, and the worker's build is shorter. New worker or beat code can run against the old schema for a few minutes. The spec gives the worker no pre-deploy step. Running `migrate` there too would race the web service's `migrate`. **Your call:** accept it, and write migrations so that new code also works before they run (the product spec only covers the other direction, old code on the new schema). Or give the worker `preDeployCommand: .venv/bin/python manage.py migrate --check`, so its deploy fails while migrations are pending, and redeploy it after the web service.
- "Render's health check may send `Host: localhost:10000`." Already under Things you should know; the spec defines the host list.
- "Uploads fall back to the local disk without a bucket" and "a missing Postmark token only fails on send." The spec asks for both: media "otherwise stays on the file system", and live Postmark/R2 credentials belong to 03-go-live. The spec's list of required production keys leaves them out.
- "`ALLOWED_HOSTS` should be required." It is empty by default so the worker can start; see Decisions.
- "gunicorn runs one sync worker." gunicorn reads `WEB_CONCURRENCY`, so this is tuning for 03-go-live under real traffic, together with Celery concurrency.
- "`logger.exception` in the health check sends a Sentry event for every failed probe during an outage." Sentry groups them into one issue, and during a database outage real requests raise the same errors. Lowering the level would drop the stack trace from the error log.
- "whitenoise caches Vite's hashed chunks for only 60 seconds." A performance point, already under Things you should know.

## Environment

- **`make` is not installed on this machine.** I ran the Makefile recipes directly through `~/.local/bin/mise exec --`: `make test` is `uv run manage.py test`, `make type-check` is `uv run mypy .`, and `make dev` is `scripts/dev.sh`.
- **"SECRET_KEY unset" in this checkout is not really unset.** mise loads `.env` into the environment, and `settings.py` reads `.env` itself with `read_env`, which only fills keys that are missing. With `env -u SECRET_KEY` in the checkout, the dev key from `.env` comes back, and `check --deploy` fails on `security.W009` (weak key) instead. To see the real missing-key failure I ran the check in a `git archive HEAD` export with no `.env`, as on Render and in CI. The unit test does the same thing in its subprocess by stubbing `read_env` out.
